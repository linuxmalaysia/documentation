ASIMP is built on a simple but powerful principle: **you can't improve what you don't measure**. Before touching a single configuration file, ASIMP establishes a cryptographically-grounded baseline of your system's security posture. After hardening is applied, it measures again — giving you concrete, side-by-side evidence of every point of improvement. This Measure → Harden → Re-Measure paradigm transforms security hardening from a one-shot "we applied a script" event into a verifiable, auditable process with before-and-after proof.

## The Three Phases

<Steps>
  <Step title="Measure (Baseline)">
    Before any change is made to your system, ASIMP runs both security engines — OpenSCAP and Lynis — against the unmodified host.

    **OpenSCAP** scans your system against the [CIS (Center for Internet Security) Level 2 Server profile](https://www.cisecurity.org/benchmark/red_hat_linux), the industry benchmark for high-security Linux workloads. CIS Level 2 covers over 200 controls spanning kernel parameters, filesystem configuration, network settings, audit policy, user account management, and service hardening. The scan produces a compliance percentage — for example, 58.4% means your system currently passes 58.4% of all CIS Level 2 controls.

    **Lynis** runs a parallel host-based audit, producing a Hardening Index (HI) score from 1 to 100. Where OpenSCAP checks standards compliance, Lynis evaluates practical hardening depth — file permissions, running services, SSH configuration, and more.

    Both scores are written to `/var/log/asimp-baseline-scores.json` before the playbook proceeds. This file is the ground truth ASIMP uses in Phase 3 to calculate improvement deltas.
  </Step>
  <Step title="Harden (Remediation)">
    With a baseline established, ASIMP applies hardening in four sequential layers — each targeting a distinct attack surface:

    1. **OS updates and package integrity** — safe system-package upgrades and `debsums` MD5 verification of every installed package file.
    2. **OpenStack `ansible-hardening` baselines** — kernel parameter tuning, PAM hardening, file permission baselines, and NTP setup drawn from OpenStack infrastructure standards.
    3. **SSH lockdown via `dev-sec.ssh-hardening`** — key exchange restrictions, `AllowTcpForwarding=no`, `MaxAuthTries=3`, `MaxSessions=2`, and hardened cipher/MAC suites.
    4. **Lynis-specific configuration fixes** — shadow file permissions, sysctl tweaks, USB storage and DCCP disablement, and compiler access restrictions.

    Before any of these layers run, ASIMP executes four **pre-flight safety checks**. If any check fails, the playbook halts immediately with a clear error — no partial changes are applied. See [Safety Gates](#safety-gates) below.
  </Step>
  <Step title="Re-Measure (Verification)">
    After hardening completes, ASIMP re-runs both OpenSCAP and Lynis against the now-hardened system using exactly the same scan parameters as Phase 1.

    The new scores are compared against the baseline saved in `/var/log/asimp-baseline-scores.json`, and a comparative scorecard is printed to the console and saved as HTML reports:

    ```
    ========================================================================
                     ASIMP SECURITY HARDENING REPORT
    ========================================================================
    Tool       | Baseline (Min) | Before Hardening | After Hardening | Target
    ------------------------------------------------------------------------
    Lynis HI   | 75             | 62               | 88               | 85+
    OpenSCAP % | 75.0%          | 58.4%            | 91.2%            | 90%+
    ========================================================================
    ```

    HTML reports are saved to `/var/log/openscap-before-report.html` and `/var/log/openscap-after-report.html` for sharing with compliance teams or auditors. If targets are not met, ASIMP flags which engine fell short so you can investigate further.
  </Step>
</Steps>

## Safety Gates

ASIMP runs four pre-flight checks at the start of Phase 2. If **any** check fails, the entire hardening phase is aborted before a single change is made.

| Check | Command | Why It Matters |
|---|---|---|
| SSH daemon syntax | `sshd -t` | Validates the current SSH configuration is parseable. Prevents SSH lockout if a prior config change introduced a syntax error. |
| Filesystem mount validation | `mount -a -f` | Dry-runs all `/etc/fstab` entries. Catches bad mount points that would cause boot failure after a kernel update. |
| Free disk space | 512 MB check on `/` | OS updates and log files require headroom. Proceeding on a near-full disk risks corrupted package installs or truncated audit reports. |
| SSH port reachability | TCP connectivity test | Confirms the SSH port is still reachable before hardening rules are applied. Prevents the scenario where tightened firewall rules silently block your own access. |

This design is intentional: **fail loudly before touching anything** is safer than partially applying a hardening set and leaving the system in an undefined state.

## Privilege Levels

ASIMP supports two privilege modes, controlled at invocation time:

| Mode | Hardening Applied | Audits Run | Typical Use Case |
|---|---|---|---|
| `full` | Yes — all four layers | Yes | Bare-metal servers, VMs, dedicated cloud instances |
| `limited` | No — Phase 2 skipped | Yes | Containers, CI/CD sandboxes, read-only audit environments |

In `limited` mode, ASIMP still runs the full Phase 1 and Phase 3 audit cycles and produces all the same reports — it just skips the system modifications in Phase 2. This is useful when you need compliance visibility in environments where modifications are managed by an external process (e.g., a golden image pipeline), or when you're running ASIMP in a container where kernel-level changes aren't meaningful.

## Output Artifacts

Every ASIMP run produces a consistent set of output files on the target host:

| Artifact | Location | Description |
|---|---|---|
| Baseline scores JSON | `/var/log/asimp-baseline-scores.json` | Pre-hardening OpenSCAP and Lynis scores; used as the comparison baseline in Phase 3 |
| OpenSCAP HTML (before) | `/var/log/openscap-before-report.html` | Human-readable CIS compliance report from Phase 1 |
| OpenSCAP HTML (after) | `/var/log/openscap-after-report.html` | Human-readable CIS compliance report from Phase 3 |
| OpenSCAP XML results | `/var/log/openscap-before-results.xml` | Raw XCCDF scan data; importable into compliance management tools |
| Lynis report | `/var/log/lynis-report.dat` | Full Lynis audit data; used to extract the Hardening Index score |
| debsums log | `/var/log/debsums.output` | MD5 verification results for all installed package files |
| Remediation scripts | `/var/log/remediate-<release>-latest.sh` | OpenSCAP-generated remediation scripts — **generated for review only, never auto-applied** |

<Note>
  Remediation scripts at `/var/log/remediate-<release>-latest.sh` are produced by OpenSCAP for your review. ASIMP deliberately does not auto-apply them — some SCAP remediations are destructive or environment-specific, and they should be evaluated and selectively executed by a human operator.
</Note>
