Phase 2 applies hardening in four distinct, sequential layers — each targeting a specific attack surface on your Linux system. The layers are ordered deliberately: OS-level integrity comes first, network attack surface comes last, with system baselines and service hardening in between. Understanding exactly what changes are made helps you plan your rollout, communicate scope to stakeholders, and make informed decisions about which layers to enable in your environment.

---

## Layer 1: OS Updates and Package Integrity

**Ansible role:** `update-ubuntu-ASIMP` / `update-rhel-ASIMP`

This layer ensures the system is running the latest available security patches and that no installed package files have been silently modified since installation.

### OS Package Updates

- On **Debian/Ubuntu**: runs `apt-get upgrade` (safe-upgrade) — installs available updates without removing packages or introducing new dependencies unsafely.
- On **RHEL/CentOS/Rocky**: runs `dnf update` with equivalent safe-upgrade semantics.

Updates run **asynchronously** so they don't block the rest of the playbook while large package downloads complete.

### Package Integrity Verification with debsums

After updates complete, ASIMP installs and runs [`debsums`](https://manpages.ubuntu.com/manpages/jammy/man1/debsums.1.html) on Debian/Ubuntu systems. `debsums` computes the MD5 checksum of every file installed by every `.deb` package and compares it against the checksum recorded in the package manifest at install time.

Any file that has been modified — whether by an attacker, a misconfigured script, or an incomplete update — will produce a checksum mismatch.

Results are saved to:

```text
/var/log/debsums.output
```

Review this file after a run to identify any unexpected package file modifications.

## Layer 2: OS Baseline Hardening

**Ansible role:** `ansible-hardening` (from OpenStack Infrastructure)

This layer applies system-wide configuration baselines drawn from OpenStack's battle-tested infrastructure hardening standards. It targets the kernel, filesystem, and authentication subsystems.

### What Gets Configured

- **Kernel parameters (sysctl)** — hardens network stack behaviour, disables kernel pointer exposure, restricts `ptrace` scope, and sets other security-relevant kernel tunables.
- **File permission baselines** — ensures sensitive system files (`/etc/passwd`, `/etc/cron.*`, `/etc/hosts.allow`, etc.) have correct ownership and mode bits.
- **PAM configuration** — strengthens password complexity requirements, account lockout policy, and session controls.
- **AIDE initialisation** — optionally initialises the [AIDE](https://aide.github.io/) intrusion detection database, establishing a filesystem integrity baseline for future change detection.
- **Chrony NTP synchronisation** — configures time synchronisation, which is required for accurate audit log timestamps and Kerberos/certificate validity.

## Layer 3: SSH Hardening

**Ansible role:** `dev-sec.ssh-hardening` (version 9.7.0)

SSH is the primary remote access vector on most Linux servers — and the most common target for brute-force, credential stuffing, and protocol downgrade attacks. This layer locks down the SSH daemon to permit only strong cryptographic primitives and restrict abuse vectors.

### Key Exchange Algorithms

Only the following KEX algorithms are permitted:

```text
curve25519-sha256@libssh.org
diffie-hellman-group-exchange-sha256
```

Older and weaker algorithms (including `diffie-hellman-group1-sha1` and `diffie-hellman-group14-sha1`) are disabled.

### SSH Daemon Configuration Changes

| Setting | Value Set | Rationale |
|---|---|---|
| `AllowTcpForwarding` | `no` | Prevents SSH from being used as a tunnelling proxy |
| `MaxAuthTries` | `3` | Limits brute-force attempts per connection |
| `MaxSessions` | `2` | Reduces per-connection multiplexing abuse surface |
| Ciphers | Strong only (AES-GCM, ChaCha20) | Removes CBC-mode and RC4 ciphers |
| MACs | Strong only (HMAC-SHA2-256/512) | Removes MD5-based MACs |

<Warning>
  SSH hardening is protected by a mandatory pre-flight `sshd -t` syntax check that runs before Phase 2 begins. If the current SSH configuration fails syntax validation, ASIMP halts immediately without making any changes. This prevents the scenario where a pre-existing SSH config error, combined with hardening changes, would lock you out of the host entirely.
</Warning>

## Layer 4: Lynis-Specific Fixes

**Ansible role:** `lynis-ansible`

This layer addresses the specific findings that Lynis commonly flags on default Linux installations — the practical hardening gaps that don't always appear in CIS benchmarks but materially reduce your Hardening Index.

### Shadow File and Authentication Permissions

Tightens permissions on `/etc/shadow`, `/etc/shadow-`, `/etc/gshadow`, and `/etc/gshadow-` to `000` (root-only, no read for any user including root via normal file access). Also validates `/etc/passwd` and group file permissions.

### Kernel sysctl Hardening

Applies a set of sysctl parameters targeting network-based attack vectors:

```ini
# Disable IP forwarding (this is not a router)
net.ipv4.ip_forward = 0

# Enable SYN flood protection
net.ipv4.tcp_syncookies = 1

# Disable ICMP redirects
net.ipv4.conf.all.accept_redirects = 0
net.ipv6.conf.all.accept_redirects = 0

# Disable source routing
net.ipv4.conf.all.accept_source_route = 0
```

### Disabling Unused Kernel Modules

Prevents loading of filesystem and protocol modules that have no legitimate use on a server and represent unnecessary kernel attack surface:

```text
# Disabled via /etc/modprobe.d/
usb-storage    # Prevents data exfiltration via USB drives
dccp           # Datagram Congestion Control Protocol — rarely needed
```

### Compiler Access Restrictions

Restricts access to system compilers to `root` only:

```text
/usr/bin/gcc   → mode 750, owner root
/usr/bin/as    → mode 750, owner root
```

This reduces the usefulness of a compromised non-root account for compiling local privilege escalation exploits or custom tooling.

### Insecure Protocol Hardening

Disables legacy protocol services that should not be running on a hardened server (e.g., `rsh`, `telnet` where installed), and validates that `inetd`/`xinetd` services are disabled if not explicitly required.

## Controlling What Gets Applied

All four layers expose Ansible variables that let you selectively enable or disable individual components. Key variables include:

| Variable | Default | Effect |
|---|---|---|
| `upgrade_ubuntu_check` | `true` | Enables Layer 1 package updates |
| `safe_upgrade_ubuntu_check` | `true` | Runs safe (non-destructive) upgrades only |
| `debsums_ubuntu_check` | `true` | Enables debsums package integrity verification |
| `security_enable_firewalld` | `false` | Enables firewalld configuration in Layer 2 |

See the [Variables Reference](/configuration/variables) for the full list of tuneable parameters.

## Limited Mode (Containers and Sandboxes)

When ASIMP is invoked with `privilege_level: limited`, **Phase 2 is skipped entirely**. The playbook executes Phase 1 (Measure) and Phase 3 (Re-Measure) as normal, producing a full audit report and scorecard, but no system modifications are made.

This mode is designed for:

- **Container environments** where kernel-level sysctl changes aren't effective and modifying the container image is the responsibility of a separate pipeline.
- **CI/CD sandboxes** where you need compliance visibility without side-effecting the build environment.
- **Read-only audit runs** where your change-management process requires human approval before any hardening is applied.

In limited mode, the scorecard will show identical Before Hardening and After Hardening values — a clear signal that the audit ran successfully in audit-only mode.
