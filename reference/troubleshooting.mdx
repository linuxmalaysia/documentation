This guide covers the most common issues encountered when running ASIMP, with specific error messages and step-by-step fixes.

<Note>
  For all connection issues, always test with `ansible all -i hosts.ini -m ping` before running the full playbook. A passing ping confirms inventory, SSH keys, and host reachability are all correct before you invest time in a full run.
</Note>

<AccordionGroup>

<Accordion title="OpenSCAP datastream not found">

**What happens:** ASIMP sets `openscap_scan_supported: false` and skips the OpenSCAP scan. The Lynis audit still runs and the scorecard is produced using Lynis data only.

**Fix on Ubuntu/Debian:**

ASIMP attempts to download the SCAP Security Guide automatically. Ensure the target host has internet access, or pre-install the package manually:

```bash
sudo apt-get install ssg-debian
# or, for broader coverage:
sudo apt-get install scap-security-guide
```

**Fix on RHEL / CentOS / Rocky / AlmaLinux:**

The SCAP Security Guide is not auto-downloaded on RHEL-family systems. Install it manually:

```bash
sudo dnf install scap-security-guide
```

**Verify the datastream files are present:**

```bash
ls /usr/share/xml/scap/ssg/content/
```

You should see files such as `ssg-ubuntu2204-ds.xml` or `ssg-rhel9-ds.xml` depending on your OS. If the directory is empty or does not exist, the package did not install correctly — check your package repository configuration.

</Accordion>

<Accordion title="SSH connection refused or timeout">

**Symptoms:** Tasks fail with `ssh: connect to host ... port 22: Connection refused` or the playbook hangs waiting for a connection.

**Step 1 — Test connectivity first:**

```bash
ansible all -i hosts.ini -m ping
```

**Step 2 — Work through the checklist:**

- **SSH service running?** On the target: `sudo systemctl status sshd`
- **Correct host/port in inventory?** Check `ansible_host` and `ansible_port` in `hosts.ini`
- **Firewall allowing SSH?** On the target: `sudo ufw status` (Ubuntu) or `sudo firewall-cmd --list-ports` (RHEL)
- **SSH key accepted?** Try connecting manually: `ssh -i ~/.ssh/your_key user@host`
- **Password auth needed?** Add `-k` to your `ansible-playbook` command to prompt for SSH password

**Step 3 — Check the specific port:**

```bash
nc -zv <host> 22
```

If this fails, SSH is not reachable at all — the issue is network or firewall level, not Ansible configuration.

</Accordion>

<Accordion title="Become / sudo permission denied">

**Symptoms:**

- `sudo: a password is required`
- `become method: sudo not found`
- `Missing sudo password`

**Cause:** Either the `-K` flag was omitted, the SSH user does not have sudo access, or sudo is not installed on the target.

**Fix:**

Always include `-b -K` when running ASIMP:

```bash
ansible-playbook -i hosts.ini -b -K play.yml
```

**Verify sudo works for your user:**

```bash
ansible all -i hosts.ini -m ping -b -K
```

If this still fails, confirm the user has a `sudoers` entry on the target:

```bash
# On the target host:
sudo visudo
# Ensure your user or group appears, e.g.:
# youruser ALL=(ALL) NOPASSWD: ALL
# or:
# %sudo ALL=(ALL:ALL) ALL
```

</Accordion>

<Accordion title="Insufficient disk space error">

**Symptom:** ASIMP halts with a `CRITICAL` message about insufficient disk space before any hardening runs.

**Check current usage:**

```bash
df -h /
```

You need at least **512 MB** free on `/`. If you are below that threshold, free space before re-running ASIMP.

**Common ways to free space:**

```bash
# Clean apt package cache (Ubuntu/Debian)
sudo apt-get clean
sudo apt-get autoremove

# Vacuum old journal logs
sudo journalctl --vacuum-size=1G

# Check what is consuming space
sudo du -sh /* 2>/dev/null | sort -rh | head -20
```

Once you have freed sufficient space, re-run ASIMP. The disk space check will pass and the playbook will continue normally.

</Accordion>

<Accordion title="SSH daemon config already broken (sshd -t fails)">

**Symptom:** ASIMP halts at the pre-flight SSH syntax check before any hardening runs. This means your SSH config had syntax errors **before** ASIMP touched it.

**Diagnose the existing errors:**

```bash
sudo sshd -t
```

This prints every syntax error found in `/etc/ssh/sshd_config` and any included files.

**Fix:**

```bash
# Open the config
sudo nano /etc/ssh/sshd_config

# After editing, re-validate
sudo sshd -t

# Repeat until sshd -t exits cleanly (no output, exit code 0)
```

Once `sshd -t` exits cleanly, re-run ASIMP — the pre-flight check will pass and the playbook will proceed.

<Warning>
  Do not restart `sshd` until `sshd -t` passes. Restarting with a broken config will drop your SSH session and may lock you out of the host.
</Warning>

</Accordion>

<Accordion title="Lynis not installed / audit skipped">

**Symptom:** The Lynis audit step is skipped or fails with a package installation error.

**In full privilege mode**, ASIMP installs Lynis automatically via the system package manager. If that installation fails, check package repository availability:

```bash
# Ubuntu/Debian
sudo apt-get update
sudo apt-get install lynis

# RHEL / CentOS / Rocky / AlmaLinux
sudo dnf install lynis
```

If `lynis` is not available in the default repositories, you may need to enable EPEL (on RHEL-family systems):

```bash
sudo dnf install epel-release
sudo dnf install lynis
```

**Verify Lynis is working:**

```bash
lynis --version
sudo lynis audit system
```

</Accordion>

<Accordion title="debsums shows CHANGED files">

**Symptom:** The `update-ubuntu-ASIMP` role reports files with a `CHANGED` status in the debsums output.

**This is not an ASIMP error.** `CHANGED` means the installed file on disk differs from the original file shipped in the package. This can indicate:

- A legitimate configuration change made by an administrator or another tool
- Unexpected modification — potentially a sign of tampering

**Investigate each changed file individually** before taking action. To view all changed files:

```bash
sudo debsums --changed
```

**To restore a specific package's files to their original state:**

```bash
sudo apt-get install --reinstall <package-name>
```

Treat `CHANGED` results as findings to investigate, not errors to dismiss.

</Accordion>

<Accordion title="Playbook runs for a very long time">

**This is usually normal.** ASIMP performs several inherently slow operations:

- **Package upgrades** — upgrading many packages on a large system takes time
- **debsums verification** — checking package integrity across all installed packages is I/O-intensive; debsums runs asynchronously to avoid SSH timeout
- **OpenSCAP scan** — a full CIS Level 2 profile scan typically takes **5–15 minutes** depending on system size

**If the playbook appears to hang:**

Check whether an async task is still running in the background on the target host:

```bash
# On the target host
ps aux | grep -E 'debsums|oscap|lynis'
```

**To disable debsums if it is consistently timing out:**

Set `debsums_ubuntu_check: no` in your vars or inventory:

```yaml
# group_vars/os_Ubuntu.yml
debsums_ubuntu_check: no
```

If the `async` timeout value in the role needs to be increased for very large systems, edit the `async:` value in the `update-ubuntu-ASIMP` role tasks.

</Accordion>

<Accordion title="RHEL / Rocky / AlmaLinux: OpenSCAP profile not found">

**Symptom:** OpenSCAP scan fails with a profile-not-found error on RHEL-family systems.

**Install the SCAP Security Guide:**

```bash
sudo dnf install scap-security-guide
```

**Verify the datastream file and available CIS profiles:**

```bash
# Check the datastream file exists (adjust for your RHEL version)
ls /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml

# List available CIS profiles
oscap info /usr/share/xml/scap/ssg/content/ssg-rhel9-ds.xml | grep cis
```

You should see profiles such as `xccdf_org.ssgproject.content_profile_cis` and `...cis_l2_server`. If no CIS profiles appear, your `scap-security-guide` package version may be too old — update it:

```bash
sudo dnf update scap-security-guide
```

</Accordion>

<Accordion title="Running in a container or CI pipeline">

**Symptom:** ASIMP fails or skips tasks when running in a Docker/Podman container or a CI sandbox (e.g. GitHub Actions, Google Jules).

**Option 1 — Use the mock script (recommended for CI):**

```bash
./tools/mock-asimp.sh
```

This standalone script simulates the full Measure → Harden → Re-Measure loop and produces mock scorecards and a `SECURITY_AUDIT_REPORT.md` in `data/asimp_mock/`. No root access required.

**Option 2 — Run the localhost playbook directly:**

```bash
ansible-playbook --connection=local play-localhost.yml
```

ASIMP automatically detects limited privileges inside containers and sandboxes. In limited mode, Phase 2 hardening is skipped, but Phase 1 and Phase 3 auditing still run and produce a scorecard.

</Accordion>
