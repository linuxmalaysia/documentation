Before ASIMP applies any hardening in Phase 2, it runs four mandatory safety checks. If any check fails, the playbook halts immediately — protecting you from SSH lockout, unbootable systems, and disk exhaustion. No hardening tasks execute until all four checks pass.

---

## Why Safety Checks Matter

Automated hardening touches some of the most sensitive areas of a Linux system: SSH configuration, filesystem mounts, and package state. Without validation, three categories of failure are possible:

- **SSH lockout** — applying SSH hardening on top of a broken SSH config can make the host permanently unreachable over the network
- **Unbootable system** — invalid `/etc/fstab` entries cause boot failures on the next reboot
- **Disk exhaustion** — package upgrades that run out of disk space mid-operation leave packages in a corrupted, partially installed state

ASIMP's pre-flight gate catches all three risks before a single hardening task runs.

## The Four Checks

<AccordionGroup>

<Accordion title="1. SSH Daemon Syntax Check">

**Command:** `sshd -t`

This check validates the syntax of the existing SSH daemon configuration **before** ASIMP makes any changes to it. If the SSH config already contains syntax errors, applying further SSH hardening on top of it could make the situation worse — or prevent SSH from restarting at all.

**What happens:**
- ASIMP runs `sshd -t` on the target host
- If any syntax error is detected, the playbook halts with a `CRITICAL` message
- The existing SSH config must be fixed manually before ASIMP can proceed

**Why it matters:** SSH is your only path back into a remote machine. An invalid SSH config that prevents `sshd` from restarting will lock you out permanently until you can access the host via console or out-of-band management.

</Accordion>

<Accordion title="2. fstab Mount Point Validation">

**Command:** `mount -a -f`

This check validates every entry in `/etc/fstab` without actually mounting anything (the `-f` flag is a dry-run). A corrupted or invalid `fstab` entry will not cause an immediate problem — but the system will fail to boot on the next restart.

**What happens:**
- ASIMP runs `mount -a -f` on the target host
- If any mount point entry is invalid, the playbook halts with a `CRITICAL` message
- The `/etc/fstab` must be corrected before ASIMP can proceed

**Why it matters:** System hardening often involves a reboot after applying kernel and PAM changes. If `fstab` is already invalid, that reboot will result in an unbootable system — a problem entirely unrelated to ASIMP, but one that ASIMP would be blamed for.

</Accordion>

<Accordion title="3. Root Partition Disk Space">

**Threshold:** ≥ 512 MB free on `/`

This check confirms that at least 512 MB of free space is available on the root filesystem before package upgrades and security package installations begin.

**What happens:**
- ASIMP checks available space on `/`
- If free space is below 512 MB, the playbook halts with a `CRITICAL` message
- Disk space must be freed before ASIMP can proceed

**Why it matters:** Package upgrades that run out of disk space mid-operation leave the package manager in a broken state — with packages partially extracted, pre/post-install scripts failing, and the `dpkg`/`rpm` database potentially corrupted. Recovering from this state is significantly more work than freeing disk space before the run.

</Accordion>

<Accordion title="4. SSH Port Reachability">

**Behaviour:** Waits for SSH port (default `22`, respects `ansible_port`) to respond. Times out after **5 seconds**.

This check confirms that SSH is actively accepting connections on the expected port before ASIMP applies SSH hardening. If SSH is not reachable at this point, hardening changes that restart `sshd` could result in a permanently unreachable host.

**What happens:**
- ASIMP uses Ansible's `wait_for` module to test the SSH port
- If the port does not respond within 5 seconds, the playbook halts
- The SSH service and firewall rules should be verified before re-running

**Why it matters:** SSH hardening changes the server configuration and restarts `sshd`. Confirming connectivity is live before that restart ensures you are not working against an already-broken connection path.

</Accordion>

</AccordionGroup>

## What Happens on Failure

When any pre-flight check fails:

1. The playbook halts immediately with a `CRITICAL` message describing which check failed and why
2. **No hardening tasks are executed** — the system is left exactly as it was before ASIMP ran
3. The **Phase 1 audit results** (already completed before safety checks run) remain available in `/var/log/` for reference
4. Fix the underlying issue on the target host, then re-run ASIMP — it will repeat the safety checks before proceeding

---

## Safety Checks in Limited Mode

In **limited privilege mode** — which ASIMP activates automatically when running in containers, sandboxes, or as an unprivileged user — the pre-flight safety checks are skipped entirely.

This is safe because Phase 2 hardening is also skipped in limited mode. There is nothing to guard against if no system changes will be made. ASIMP will still complete Phase 1 and Phase 3 auditing and produce a scorecard.

## Manual Pre-Flight Checks

You can run the same validations manually before executing ASIMP. This is useful when diagnosing a pre-existing issue or verifying a host before adding it to your inventory.

```bash
# 1. SSH daemon config syntax
sudo sshd -t

# 2. fstab mount point validation (dry-run, no actual mounts)
sudo mount -a -f

# 3. Available space on / in kilobytes (512MB = 524288 KB)
df / --output=avail | tail -n1

# 4. SSH port reachability
nc -zv localhost 22
```

All four commands should succeed silently (exit code 0) before running ASIMP. If any command returns an error, resolve it before proceeding.
