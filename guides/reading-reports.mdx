After every ASIMP run you get three types of output: a **console scorecard** printed at the end of the playbook, **detailed HTML reports** for deep rule-by-rule inspection, and a generated **remediation script** containing the bash commands needed to close any remaining gaps. This guide walks you through each one.

## The Console Scorecard

The scorecard is printed to the terminal as the final step of Phase 3. It shows a side-by-side comparison of your system's compliance posture before and after hardening:

```text
========================================================================
                 ASIMP SECURITY HARDENING REPORT
========================================================================
Tool       | Baseline (Min) | Before Hardening | After Hardening | Target
------------------------------------------------------------------------
Lynis HI   | 75             | 62               | 88               | 85+
OpenSCAP % | 75.0%          | 58.4%            | 91.2%            | 90%+
========================================================================
Reports generated successfully:
  - OpenSCAP Before Report: /var/log/openscap-before-report.html
  - OpenSCAP After Report:  /var/log/openscap-after-report.html
========================================================================
```

### Understanding the Columns

| Column | Meaning |
|--------|---------|
| **Baseline (Min)** | The minimum acceptable score. A Before Hardening score below this value indicates the system was in a critically non-compliant state before ASIMP ran. |
| **Before Hardening** | Your system's score at the start of the run, captured during Phase 1. This becomes the permanent baseline stored in `/var/log/asimp-baseline-scores.json`. |
| **After Hardening** | Your system's score at the end of Phase 3, after all hardening tasks have been applied. This is the number that matters for compliance reporting. |
| **Target** | The goal score. An After Hardening score at or above this value means the run met its objective. |

### Score Thresholds

- **Lynis Hardening Index (HI):** Minimum acceptable score is **75**, target is **85 or higher**. The HI is an integer from 0–100 reflecting Lynis's assessment of overall system configuration quality.
- **OpenSCAP Percentage:** Minimum acceptable is **75.0%**, target is **90% or higher**. This is the ratio of passing XCCDF rules to total evaluated rules under the CIS Level 2 profile.

### What to Do if Scores Are Below Target

If your After Hardening score is below the target for either tool, open the corresponding HTML report to find which specific rules are still failing. Each failing rule includes a severity rating and fix instructions. Common reasons for remaining failures include rules that require manual intervention (bootloader changes, specific PAM configurations) or rules that conflict with your organisation's operational requirements.

## HTML Audit Reports

### Location

| Report | Path |
|--------|------|
| OpenSCAP before hardening | `/var/log/openscap-before-report.html` |
| OpenSCAP after hardening | `/var/log/openscap-after-report.html` |

### How to Open

On a machine with a desktop environment:

```bash
firefox /var/log/openscap-before-report.html
firefox /var/log/openscap-after-report.html
```

On a headless server, copy the files to your workstation first:

```bash
scp user@target-host:/var/log/openscap-before-report.html ~/Desktop/
scp user@target-host:/var/log/openscap-after-report.html ~/Desktop/
```

### What They Contain

Each HTML report is a self-contained, fully-navigable document generated by OpenSCAP from the XCCDF evaluation results. For every rule in the CIS Level 2 profile the report shows:

- **Rule title and ID** — the official CIS benchmark identifier
- **Pass / Fail / Not Checked status** — colour-coded for quick scanning
- **Severity** — High, Medium, or Low
- **Description** — a plain-language explanation of what the rule checks and why it matters
- **Fix instructions** — the remediation steps OpenSCAP recommends for failing rules

Open both the before and after reports side-by-side to clearly see which rules were remediated by ASIMP and which still require attention. Rules that move from **Fail** in the before report to **Pass** in the after report represent successful hardening outcomes.

## Baseline JSON

**Location:** `/var/log/asimp-baseline-scores.json`

This file is written at the end of Phase 1 and preserves the pre-hardening scores used for comparison throughout the run. It serves as the authoritative record of your system's compliance state before ASIMP made any changes.

Example file structure:

```json
{
  "openscap_before": 58.4,
  "lynis_before": 62,
  "timestamp": "2026-08-05T12:00:00Z"
}
```

This file is intentionally not overwritten on subsequent runs, so it retains the original baseline even if you re-run ASIMP multiple times.

## Lynis Report Files

| File | Description |
|------|-------------|
| `/var/log/lynis-report-before.dat` | Machine-readable Lynis results captured before hardening |
| `/var/log/lynis-report-after.dat` | Machine-readable Lynis results captured after hardening |

These files use a flat `key=value` format that is easy to parse in scripts and monitoring pipelines. The most important field for compliance tracking is:

```text
hardening_index=88
```

Other useful fields include `warning[]` entries (specific warnings Lynis raised), `suggestion[]` entries (non-critical improvement recommendations), and `plugin_enabled[]` (which Lynis plugins were active during the scan).

## The Remediation Script

**Location:** `/var/log/remediate-<release>-latest.sh` *(Ubuntu only)*

For example, on Ubuntu 24.04 (Noble Numbat): `/var/log/remediate-noble-latest.sh`

This script is generated by OpenSCAP directly from the XCCDF evaluation results at the end of Phase 3. It contains shell commands to fix every failing rule that OpenSCAP knows how to remediate automatically.

<Warning>
  **Do not run the remediation script automatically without reviewing it first.** Some fixes — particularly bootloader parameter changes (GRUB command-line arguments) and PAM module configuration — can make a system unbootable or lock out all user accounts if applied incorrectly on your specific hardware or configuration. Review the script in full and apply only the sections you have tested and understood.
</Warning>

To review the script interactively:

```bash
less /var/log/remediate-noble-latest.sh
```

Once you have identified specific sections you want to apply, extract and execute them individually rather than running the entire script. This gives you full control over which remediations are applied and lets you verify each change before proceeding to the next.

## debsums Output

**Location:** `/var/log/debsums.output`

`debsums` verifies the MD5 checksums of installed package files against the values recorded in the package database at installation time. ASIMP runs this check during Phase 2 as part of the package integrity assessment.

Entries in this file fall into three categories:

| Status | Meaning |
|--------|---------|
| *(no output)* | All checked files match their expected checksums — no issues found |
| `CHANGED` | The file exists but its content no longer matches the original package — possible tampering or untracked local modification |
| `MISSING` | A file that should have been installed by a package is no longer present on disk |

Any `CHANGED` or `MISSING` entries warrant investigation. `CHANGED` entries on configuration files under `/etc/` are often intentional and expected, but `CHANGED` entries on binaries under `/usr/bin/` or `/lib/` are a stronger indicator of tampering or corruption and should be investigated before trusting the hardening results.
