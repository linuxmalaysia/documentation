ASIMP detects restricted execution environments automatically and can also be invoked in an explicit mock mode — useful for testing in containers, CI pipelines, and unprivileged sandboxes where making real system changes is either impossible or undesirable. In both cases ASIMP produces a complete, realistic set of output artifacts so you can validate your configuration, inspect the report format, and integrate ASIMP into automated workflows without touching system state.

## When Sandbox Mode Activates Automatically

ASIMP probes host capabilities at the start of every run. When it cannot write to `/etc` — which is the case in most unprivileged containers and CI runner environments — it automatically sets the privilege level to **limited mode**.

In limited mode the behaviour changes as follows:

| Phase | Limited Mode Behaviour |
|-------|----------------------|
| Phase 1 — Measure | Runs normally if OpenSCAP and Lynis are installed; uses mock scores if they are not available |
| Phase 2 — Harden | **Skipped entirely** — no system changes are applied |
| Phase 3 — Re-Measure | Runs normally or uses mock scores, then generates the scorecard and reports |

<Note>
  Scores generated in limited mode are labelled **NON-AUTHORITATIVE** in the output. They are intended for testing and demonstration only and are not used for compliance gating in production workflows.
</Note>

ASIMP also auto-switches to limited mode when it detects a known unprivileged container or CI runner environment. In these environments, ASIMP writes mock results and scorecards into the workspace directory (`data/asimp_mock/`) so the playbook run completes successfully and produces a full set of output artifacts.

## Using the Mock Script

For the most direct way to simulate a complete ASIMP run without any system access at all, use the standalone mock script:

```bash
./tools/mock-asimp.sh
```

This script simulates the entire Measure → Harden → Re-Measure loop and produces output artifacts in the `data/asimp_mock/` directory, with no reads or writes outside the project folder.

### Mock Output Files

| File | Description |
|------|-------------|
| `data/asimp_mock/var/log/asimp-baseline-scores.json` | Mock pre-hardening Lynis and OpenSCAP scores |
| `data/asimp_mock/opt/report/openscap/SECURITY_AUDIT_REPORT.md` | Mock consolidated security audit report in Markdown |

### Mock Scorecard Output

The mock script produces a scorecard that mirrors what a real privileged run produces:

```text
========================================================================
                 ASIMP SECURITY HARDENING REPORT
========================================================================
Tool       | Baseline (Min) | Before Hardening | After Hardening | Target
------------------------------------------------------------------------
Lynis HI   | 75             | 62               | 88               | 85+
OpenSCAP % | 75.0%          | 58.4%            | 91.2%            | 90%+
========================================================================
Reports generated successfully:
  - OpenSCAP Before Report: /var/log/openscap-before-report.html
  - OpenSCAP After Report:  /var/log/openscap-after-report.html
========================================================================
```

This makes it straightforward to test downstream report consumers, CI assertion scripts, or dashboard integrations against realistic ASIMP output without needing a real Linux host to harden.

## Running Playbooks in Containers

When you run `play-localhost.yml` inside a container, ASIMP automatically detects the restricted privilege environment and switches to limited mode:

```bash
ansible-playbook --connection=local play-localhost.yml
```

What happens inside a container:

- ASIMP attempts to detect OpenSCAP and Lynis. If both are installed in the container image, Phase 1 and Phase 3 audits execute normally and produce real scan data.
- If OpenSCAP or Lynis are not available, ASIMP substitutes mock scores so the run completes without errors.
- Phase 2 hardening tasks that require kernel access or `/etc` write permission are skipped automatically.
- The scorecard and all report artifacts are written to the standard locations.

This behaviour makes ASIMP suitable for use in CI/CD pipeline jobs that run inside Docker or similar container runtimes, where you want to validate playbook syntax and report generation without a privileged host.

## Use Cases

Sandbox and mock mode are designed for the following workflows:

- **Testing configuration changes before a production run** — make changes to your inventory, roles, or variable files and confirm the playbook runs end-to-end before scheduling a real hardening window.
- **CI/CD pipeline integration** — validate that ASIMP produces expected output in automated pipelines without requiring a dedicated hardening target or elevated privileges in the runner.
- **Demonstrating compliance reporting to stakeholders** — generate a realistic scorecard and HTML report to show colleagues or auditors what ASIMP's output looks like before committing to a production run.
- **Learning ASIMP's output format** — explore every report artifact, understand the scorecard columns, and navigate the HTML reports without the risk of modifying a live system.

<Tip>
  Use sandbox mode to preview exactly what ASIMP's reports look like — including the scorecard layout, HTML report structure, and JSON baseline file format — before committing to a production hardening run on a real system.
</Tip>
