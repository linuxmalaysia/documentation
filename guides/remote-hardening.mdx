title: "Harden Remote Linux Hosts Across Your Infrastructure"
sidebarTitle: "Remote Hardening"
description: "Run ASIMP against one or more remote Linux servers using an Ansible inventory file, applying hardening and compliance auditing at scale."
---

`play.yml` lets you harden and audit multiple remote Linux hosts in a single run. ASIMP auto-detects each host's OS family and version, groups hosts accordingly, and applies the correct hardening roles and OpenSCAP content for that platform — so a mixed inventory of Ubuntu, Debian, and RHEL hosts is handled in one pass without manual per-host configuration.

## Prerequisites

Before running the remote playbook, confirm the following:

- A Python virtual environment is active with all dependencies installed.
- Ansible Galaxy roles are installed from `requirements.yml`.
- You have SSH access to every target host (key-based or password authentication).
- Your user account has `sudo` (passwordless or interactive) on each target host.

See the [Installation guide](/installation) for environment setup instructions.

## Running the Remote Playbook

<Steps>
  <Step title="Create Your Inventory File">
    Create a file called `hosts.ini` (or any filename you prefer) that lists your target hosts. You can group hosts by role to target them independently later:

    ```ini
    [webservers]
    web1.corp.example ansible_user=ubuntu
    web2.corp.example ansible_user=ubuntu

    [dbservers]
    db1.corp.example ansible_user=ec2-user
    db2.corp.example ansible_user=ec2-user

    [hardened:children]
    webservers
    dbservers
    ```

    Each host entry can include per-host variables such as `ansible_user`, `ansible_port`, or `ansible_ssh_private_key_file`. See the [Inventory Configuration](/configuration/inventory) reference for all supported options.
  </Step>

  <Step title="Test Connectivity">
    Before running the full playbook, verify that Ansible can reach every host in your inventory:

    ```bash
    ansible all -i hosts.ini -m ping
    ```

    A successful response looks like:

    ```text
    web1.corp.example | SUCCESS => {
        "changed": false,
        "ping": "pong"
    }
    db1.corp.example | SUCCESS => {
        "changed": false,
        "ping": "pong"
    }
    ```

    Investigate any `UNREACHABLE` or `FAILED` responses before proceeding. Common causes include incorrect usernames, missing SSH keys, or firewalls blocking port 22.
  </Step>

  <Step title="Run the Remote Playbook">
    With connectivity confirmed, launch the remote hardening playbook:

    ```bash
    ansible-playbook -i hosts.ini -b -K play.yml
    ```

    **Flag reference:**

    | Flag | Meaning |
    |------|---------|
    | `-i hosts.ini` | Path to your inventory file |
    | `-b` | Enable privilege escalation (become root) on remote hosts |
    | `-K` | Prompt for the sudo/become password before execution begins |

    If all hosts share the same sudo password you will be prompted once. If hosts use different passwords, configure `ansible_become_password` per host in your inventory instead of using `-K`.
  </Step>

  <Step title="Monitor Progress">
    Ansible streams task-by-task output for each host as the playbook runs. You will see the three ASIMP phases execute across all hosts in parallel:

    ```text
    TASK [reporting-ASIMP : Phase 1 — Run OpenSCAP baseline scan] ****************
    changed: [web1.corp.example]
    changed: [db1.corp.example]

    TASK [update-ubuntu-ASIMP : Apply all pending OS updates] ********************
    changed: [web1.corp.example]
    changed: [db1.corp.example]

    TASK [reporting-ASIMP : Phase 3 — Generate comparative scorecard] ************
    ok: [web1.corp.example]
    ok: [db1.corp.example]
    ```

    Each task line shows one of four states: `ok` (no change needed), `changed` (task applied a modification), `skipped` (not applicable to this host's OS), or `failed` (an error occurred). A `PLAY RECAP` summary is printed at the end showing the total count of each state per host.
  </Step>

  <Step title="Collect Reports">
    After the playbook completes, the HTML audit reports are stored **on each target host** at:

    - `/var/log/openscap-before-report.html` — full OpenSCAP evaluation before hardening
    - `/var/log/openscap-after-report.html` — full OpenSCAP evaluation after hardening

    To pull reports from all hosts to your local machine, use `ansible` with the `fetch` module or copy them individually with `scp`:

    ```bash
    # Copy reports from a single host
    scp ubuntu@web1.corp.example:/var/log/openscap-after-report.html \
        ./reports/web1-after.html

    # Fetch from all hosts at once using Ansible
    ansible all -i hosts.ini -m fetch \
        -a "src=/var/log/openscap-after-report.html dest=./reports/ flat=no"
    ```

    See [Reading Reports](/guides/reading-reports) for a full guide to interpreting the scorecard and HTML reports.
  </Step>
</Steps>

## Targeting Specific Hosts

Use the `--limit` flag to restrict a playbook run to a subset of your inventory without editing the inventory file itself:

```bash
# Run against the webservers group only
ansible-playbook -i hosts.ini -b -K play.yml --limit webservers

# Run against a single named host
ansible-playbook -i hosts.ini -b -K play.yml --limit web1.corp.example

# Run against multiple groups
ansible-playbook -i hosts.ini -b -K play.yml --limit "webservers,dbservers"
```

This is useful for rolling out hardening incrementally, re-running a failed host, or testing a configuration change on one machine before applying it to the full inventory.

## Using SSH Keys

If your hosts use SSH key authentication — which is recommended over password authentication — pass the private key path directly:

```bash
ansible-playbook -i hosts.ini -b --private-key ~/.ssh/id_rsa play.yml
```

You can also set the key per host inside your inventory file:

```ini
web1.corp.example ansible_user=ubuntu ansible_ssh_private_key_file=~/.ssh/web_key.pem
```

## Supported Operating Systems

ASIMP auto-detects each host's OS at runtime and applies the appropriate hardening content. Other OS families are detected but their hardening tasks are skipped with a warning.

| Operating System | Notes |
|-----------------|-------|
| Ubuntu 20.04+ | Full support. OpenSCAP Security Guide (SSG) content is downloaded dynamically if not present. |
| Debian | Full support. Uses the same SSG download path as Ubuntu. |
| RHEL 8+ | Full support. Uses pre-installed SSG datastreams from the `scap-security-guide` package. |
| CentOS | Full support. |
| Rocky Linux | Full support. |
| AlmaLinux | Full support. |

<Warning>
  **Pre-flight safety checks run before hardening on every host.** ASIMP validates SSH daemon configuration syntax (`sshd -t`), checks `/etc/fstab` integrity (`mount -a -f`), confirms at least 512 MB of free space on `/`, and verifies SSH port reachability. If any check fails on a given host, that host's Phase 2 hardening is aborted immediately while hardening continues on all other hosts. Review the play output carefully for any hosts that show pre-flight failures.
</Warning>
